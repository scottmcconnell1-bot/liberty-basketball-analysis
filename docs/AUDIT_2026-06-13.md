## 2. Code Quality Assessment

### app.py (226 lines)

| # | Severity | Issue |
|---|----------|-------|
| C1 | **High** | `@app.before_request` runs `init_db()` check on EVERY request. Should be a startup check, not per-request. Hits filesystem on every API call. |
| C2 | **High** | `game_id` in events/analysis_runs/detections tables is TEXT, but in games/scheduled_games it's INTEGER. Inconsistent typing. The `save_event` endpoint defaults `game_id` to `"default_game"` (string). This will cause data integrity issues in Phase 5 when stats aggregation joins events → games. |
| C3 | Medium | No input validation beyond checking required fields. No date format validation, no length limits. SQL injection is prevented by parameterized queries (good). |
| C4 | Medium | Line 223: `print(app.url_map)` left in production code. |
| C5 | Medium | No error handling on most API endpoints. If DB is locked or query fails, app returns 500 with no useful message. |
| C6 | Low | DB connections manually opened/closed in each route. No connection pooling or context manager. Functional but fragile under concurrent requests. |

### schema.sql (161 lines)

| # | Severity | Issue |
|---|----------|-------|
| S1 | **High** | `events.game_id` and `stats.game_id` are TEXT, but `games.id` is INTEGER. When Phase 5 joins these for box scores, type mismatch will cause issues. Should be `INTEGER REFERENCES games(id)`. |
| S2 | Medium | `practices.end_time` is TEXT while `start_time` is TIME. Should be TIME for consistency. |
| S3 | Medium | `scheduled_games` has `season_id` foreign key but no `ON DELETE CASCADE` or `ON UPDATE`. Deleting a season will orphan scheduled_games. |
| S4 | Low | No indexes defined. Queries on `events WHERE game_id = ?` and `scheduled_games WHERE season_id = ?` will slow down as data grows. |

### season_management.py / scheduled_games.py

**Assessment:** Clean, straightforward CRUD. Good docstrings. Consistent pattern. The `edit_*` functions with dynamic UPDATE building are well-implemented.

| # | Severity | Issue |
|---|----------|-------|
| M1 | Low | `list_seasons()` and `list_scheduled_games()` set `conn.row_factory = sqlite3.Row` then reset to `None`. If another function uses the same connection between those calls, behavior is unpredictable. |

## 3. Architecture Assessment

### Sound Decisions
- SQLite is right for a single-coach, single-machine tool
- Feature flags in config.py is excellent for phased development
- `schema.sql` as single source of truth is correct
- Server-rendered HTML (no JS framework) is appropriate
- The phased roadmap (P0→P7) is well-scoped

### Architectural Concerns

| # | Concern | Detail |
|---|---------|--------|
| A1 | Film tool integration gap | `film-tool-v2026-04-23-Tagger_Finished.html` is served at `/` but not integrated with Flask's game/season context. Phase 2.5 is supposed to wire this together, but there's no clear plan for how the HTML file gets game_id context from Flask. This is the biggest gap between current state and Phase 2.5. |
| A2 | No test infrastructure | Zero tests. IMPLEMENTATION_PLAN mentions `tests/test_event_pipeline.py` but it doesn't exist. For a project handed between AI agents, tests are the safety net. |
| A3 | No `.gitignore` | `film_analysis.db` is in repo root with no `.gitignore`. If anyone runs the app, the DB could get committed. Must add `.gitignore`. |
| A4 | Bloated requirements.txt | 60 packages including CUDA, torch, torchvision, ultralytics — for a Phase 2 app that's just serving HTML and doing CRUD. CV pipeline deps are bleeding into the web app. Should separate (e.g., `requirements-web.txt` and `requirements-cv.txt`). |
| A5 | Legacy files in root | `tracker_assigner.py`, `ai_analyzer.py`, `event_generator.py` are pre-Phase 1 code sitting in root. Creates noise and makes it hard to distinguish active vs. legacy. |

## 5. Summary

### What's Good
- Documentation is the strongest asset — VISION, ROADMAP, AUTHORITY, and DECISIONS are exactly the right structure
- Authority boundaries are clear and well-enforced on paper
- Core CRUD modules are clean and well-written
- The phased approach with feature flags is mature

### Priority Fixes

1. **Fix `game_id` type mismatch** (C2 + S1) — will cause real bugs in Phase 5
2. **Add `.gitignore`** (A3) — prevent DB and pyc commits
3. **Fix `@app.before_request`** (C1) — performance issue
4. **Separate CV deps from web deps** (A4) — cleanliness
5. **Clean up root directory** — move legacy code and data files
6. **Update PROGRESS.md** (D2) — it's stale
7. **Create test stub** (A2) — even minimal tests help
8. **Mark legacy files** — add header comment indicating what phase they're for

### Bottom Line
The project is in solid shape for Phase 2 completion. The documentation is genuinely good — a new AI *can* onboard from these docs in ~10 minutes as VISION.md claims. The code quality is acceptable for a CRUD app. The main risks are the `game_id` type inconsistency (will bite in Phase 5) and the lack of `.gitignore` (operational risk). File organization needs a cleanup pass before a new ChatGPT starts working in here.
