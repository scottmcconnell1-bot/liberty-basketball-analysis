Review of the NFHS fix (read-only; no files changed):

Q1. The "final file exists => download finished" reasoning checks out against yt-dlp's actual postprocessor flow. The fixup (and merger) write to <final-stem>.temp.<ext> and only then rename into place, so the final name is only produced after all fragments/sections completed; fragments live at <final>.part and are never at the final path. So on a non-zero exit, final-exists means the download phase finished and the failure was post-download (typically the MP4 fixup / "Conversion failed"). Native HLS, ffmpeg downloader, and --download-sections all use this same fragment-then-rename machinery, so the trigger condition is sound. No partial video can be accepted through the final-file path. Minor residual: a stale final from an earlier run of the same game id could exist, but names are per-game and content is re-validated.

Q2. For its purpose the check is adequate: final-exists already implies fragment completeness, so probe + duration>0 + mp4/mov + decode-last-5s is a sound integrity gate against truncation/corruption. I would still add an expected-duration check as defense-in-depth (compare recovered duration vs NFHS/yt-dlp metadata for full games, vs the requested section length for clips; accept within tolerance, reject if grossly short). If no expected duration is available, current behavior stands.

Q3. Replacing is safe: the candidate (leftover temp or remux output) is validated before the replace; remux output is verified via _is_good_mp4 before swapping. Lock risk is handled by the retry loop. Only real concern: remux of an ~8 GB file writes a second ~8 GB temp (transient ~16 GB peak) — acceptable, though deleting the invalid final before remux would halve peak usage.

Q4. Before Scott relies on it: clean up leftover/fix temp files on the failure return path (currently only done on success paths); add the expected-duration check above; consider trimming disk peak during remux.
